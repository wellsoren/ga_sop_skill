# Plan Mode SOP（单 Agent 版 v2.6）

> [运行环境] 本机 GA 为单 Agent，无 subagent、不支持并行委托。所有环节由主 agent 自执行，但守住 3 条不变原则：
> 1) 探测只读，禁改文件/副作用操作，≤10 次工具调用；
> 2) 验证必须有实际工具调用取证（非叙述），最后输出 VERDICT: PASS/FAIL/PARTIAL；
> 3) 保持主 agent 上下文干净：探测/验证/搬砖活输出一律压缩为"结论+证据路径"落盘，禁贴大段原始输出。
> 判定标准：无工具调用证据的 PASS 按 FAIL 处理；禁止无证据声称完成。

## 一、前置条件

### 1.1 何时用（官方 7 条件 + 用户指令，满足任一）
> 源自 EnterPlanModeTool prompt.ts——"Getting user sign-off on your approach before writing code prevents wasted effort and ensures alignment"

| # | 条件 | 例子 |
|---|------|------|
| 1 | **新功能实现**：添加有意义的功能 | "加个退出按钮"→放哪？点击后做什么？ |
| 2 | **多个有效方案**：任务可多种方式解决 | "给 API 加缓存"→Redis/内存/文件？ |
| 3 | **修改现有代码**：影响既有行为/结构 | "重构这个组件"→目标架构是什么？ |
| 4 | **架构决策**：需要在模式/技术间选择 | "加实时更新"→WebSocket vs SSE vs 轮询 |
| 5 | **多文件改动**：预计触碰 >2-3 个文件 | "重构认证系统" |
| 6 | **需求不明确**：先探索才能理解全貌 | "让 App 更快"→先 profile 找瓶颈 |
| 7 | **用户偏好影响方向**：实现可以多种走法 | 想 AskUserQuestion 澄清时→改用 Plan 模式 |
| 8 | **用户明确要求**：用户明说用 plan/规划模式 | "用plan模式做这个" / "先规划再执行" / "走plan流程" |

> ⚠ 条件 8 为**用户指令优先**：即使任务简单（如单文件修改），用户明确要求走 plan 模式也必须进入规划流程，不得因 §1.2 简单任务规则自行跳过。

### 1.2 何时不用（直接做）
- 单行/少行修复（typo、明显 bug、小调整）
- 单个函数且需求明确
- **研究/信息收集类任务**（搜索/读文件/理解代码库）——官方 ExitPlanMode prompt 明示：不规划实现步骤就不该进入"提交计划"流程；只需输出发现，不建计划

### 1.3 环境依赖
- 单 Agent，无 subagent → 子代理 Plan 模式（planAgent）不可用，由主 agent 自执行
- 无需额外 API Key / 软件依赖

## 三、快速参考

```markdown

→ ask_user 确认门(⛔未确认不得执行) → 按开态项([ ]/[D]/[?])逐项执行 → [VERIFY] 独立评委 → VERDICT → 收口
```

**进入规划态（唯一入口）**：
```python
handler.enter_plan_mode("./plan_XXX/plan_XXX.md")   # inline_eval=True 时自动注入
```

> 新建默认：`./plan_XXX/plan_XXX.md`（XXX=目录短名）。已有 `plan_XXX/plan.md` 可继续 `enter_plan_mode(原路径)`，不强制重命名。

## 四、执行流程

### 阶段 0：判定（先于一切）
按 §1.1 / §1.2 判定：**该用** → 进入阶段 1；**不该用** → 直接做，不建 plan。
> ⚠ 研究类任务禁止走"提交计划审批"流程（官方明示）。
> 🔴 **用户明确要求用 plan 模式**（"用plan模式"、"先规划再执行"等）→ 无条件进入阶段 1，不因简单任务规则跳过（§1.1 条件 8）。

### 阶段 1：探索态（只读，官方 6 步的前 3 步）
> 官方 6 步：①彻底探索 ②识别现有模式/类似功能 ③考虑多方案及权衡 ④AskUserQuestion 澄清 ⑤设计具体实现策略 ⑥ExitPlanMode 提交审批

目标 = 搞清：①环境现状 ②可用 SOP ③关键不确定点。**只读禁改文件，≤10 次工具调用**。

1. `mkdir plan_XXX/`（XXX=任务英文短名）；从 L1 Insight 索引匹配领域 SOP；更新 checkpoint：`[任务] XXX | [需求] 一句话 | [约束] ... | [匹配SOP] ... | [进度] 探索态`。
2. 探测写入 `plan_XXX/exploration_findings.md`（格式 `## 环境现状 / ## 关键发现 / ## 扫描范围确认 / ## 风险/不确定点`）；代码类=文件结构/依赖/入口，浏览器类=页面状态/可交互元素，自动化类=which/pip/路径/权限，数据类=首尾5行+总量。
   **🔴 扫描范围确认（V2.3 客观校验）**：必须写清 `扫描方式: 递归全量/仅顶层 + 目标对象数 N + 是否含子目录`。代码类=文件树范围(含/不含子目录)、数据类=样本量/总量口径、网页类=页面数/链接范围。**写不出客观数字 = 探索不足，禁止进规划态**。
3. **访谈阶段（V2 特性）**：需求不明确时，先 `ask_user` 澄清（等价 AskUserQuestion）再继续探索——不要带着模糊需求瞎探索。
4. 自审方向（显式收敛判定，**三项全满足**才进规划态）：
   - 探索发现足以支撑计划（关键文件/可复用模式/依赖已识别；**且 exploration_findings.md 含「扫描范围确认」客观数字**——无数字=不满足）
   - 不确定点已澄清 或 已标 ⚠待确认（不留模糊需求进规划）
   - 实现路径初步清晰（能列出执行计划骨架）
   → 全满足 → 进入规划态；否则回到步骤 3 补充澄清（勿无脑多探）。

**🔴 严格只读约束**（源自 planAgent 系统提示）：探索阶段**禁止**：创建新文件（除 plan_XXX 内计划文件）、修改/删除/移动/复制任何文件、创建临时文件、使用重定向(`>`/`>>`/`|`)/heredoc 写文件、运行任何改变系统状态的命令。只允许读类命令（ls/git status/cat/head/tail/grep/find/文件读）。

**🔴 探索态工具白名单（tools_mode: strict，覆盖 SOP 级 lax）**：本阶段只允许 `code_run / file_read / file_patch / file_write / ask_user / update_working_checkpoint`；**禁 start_long_term_update**（记忆蒸馏属执行态动作，探索期只读不改）。⚠ 任何写操作（file_patch/file_write/code_run 内）**仅限 plan_XXX/ 目录**（探索发现/计划文件）；plan_XXX/ 外一律只读。每轮工具调用前自检是否越界，越权 → 换允许工具或标 [SKIP]。

### 阶段 2：规划态（含审查门）
先读匹配到的领域 SOP 再写 plan。允许"⚠待确认"，禁止以"没调研清楚"推迟。

**[D] 压缩标注**（符合任一即标）：读大量代码/文件(>3个或>100行) | 浏览网页提取信息 | ≥3次重复操作 | 跑测试/构建并分析输出。标 [D] 表示该步执行时输出必须压缩为"结论+证据路径"。不标: 读/更新计划文件、单文件小改、ask_user、简单一次性命令。

**计划文件格式**（v2.0 含多方案节 + 关键文件节）：
```markdown
<!-- EXECUTION PROTOCOL (每轮必读，这是你的执行指南)
1. file_read(计划文件)，找到第一个开态项（[ ] / [D] / [?]；跳过 HTML 注释块内示例）
2. 该步标注了SOP → file_read 该SOP的🔑速查段
3. 执行该步骤 + Mini验证产出
4. file_patch 开态 → [✓ 一句话结论 | 证据: path或cmd或决策摘要] 或 [✗ 原因] / [SKIP …]；禁止裸 [✓]；然后回步骤1
5. 所有步骤（包括验证步骤）标记完成后 → 终止检查：file_read(计划文件)确认 0 个开态残留（正文无 [ ]/[D]/[?]；完成态为 [✓…]/[✗…]/[SKIP…]）
⚠ 禁止凭记忆执行 | 禁止跳过验证步骤 | 禁止未经终止检查就结束 | 禁止停下来输出纯文字汇报

- 不确定点：ZZZ

- 方案B：...（优点/缺点）
```

**自检清单**（主 agent 逐项）：
- □ 判定正确（§1.1 任一条件成立，且非研究类任务）
- □ 探索发现都反映在 plan；不确定点已在访谈阶段澄清或标"⚠待确认"
- □ 多方案权衡节有 ≥2 方案 + 推荐理由
- □ 每步 SOP 标注合理；步骤依赖正确（无隐含依赖漏写）
- □ 高风险步骤（SOP:无/不可逆）有清晰思路
- □ 粒度合适（禁止"处理所有文件"，必须展开具体条目）
- □ 复杂/繁琐步骤已标 [D]（输出压缩）
- □ 含"关键文件"节（3-5 个）
- □ 含"验证检查点"section 且有 [VERIFY] 步骤（强制）

### 阶段 3：用户确认门（= CC ExitPlanMode 审批）
> 源码对应：ExitPlanModeV2Tool.checkPermissions → `behavior: 'ask', message: 'Exit plan mode?'`——**计划未经用户批准不得执行**。

**🔴 提交前硬校验**（对应 ExitPlanModeV2Tool.call 无 plan 文件即 throw 的代码级强制）: `ask_user` 前必须 `file_read(计划文件)` 全文核验 3 项：
- ① 含执行计划开态项（`[ ]`/`[D]`/`[?]` 任一）  ② 含「关键文件」节  ③ 含「验证」节
- 任一不满足 → 回规划态补齐，**不得**进入 ask_user 提交（防残计划过门）。

**🔴 CHECKPOINT（用户确认门）**: `ask_user` 确认 plan 后才能执行。⛔ 未确认不得执行。
- 用户批准 → 转执行态，更新 checkpoint：`[执行] 计划文件 | 当前：步骤1`
- 用户修改意见 → 回规划态修正计划文件，重新过审查门
- 用户拒绝 → 任务终止或换方向

### 阶段 4：执行态循环（Todo 思想 = TodoWriteTool）
> 核心: 连续执行, 不停顿汇报。做完一步立即 file_read(计划文件) 找下一个**开态**项（`[ ]`/`[D]`/`[?]`），直到全部完成。

**任务图语义映射**（不新增标记字母；禁止第二套 pending/running 列表）：

| 语义 | checkbox | 说明 |
|------|----------|------|
| pending | `[ ]` / `[D]` / `[?]` | 未完成；`[D]`=搬砖压缩，`[?]`=条件分支 |
| running | （不落盘专用符） | = 正文**第一个开态**项；可用 checkpoint 简注当前步 |
| completed | `[✓ 结论 \| 证据: …]` | 证据=路径 **或** 命令/退出码 **或** 决策摘要；**禁止裸 [✓]** |
| failed | `[✗ 原因]` | 失败不静默；依赖项可 `[SKIP]` |
| killed | 剩余开态 → `[✗ 用户终止]` | 用户中止时**一律**改完；终止检查仍 0 开态；VERDICT 可 PARTIAL |

**Mini 验证落盘（强制）**：
1. 每步执行后必须把结果写进计划文件同行（或紧随缩进行），再进入下一步。
2. 成功：`[✓ 一句话结论 | 证据: …]`；失败：`[✗ 原因]`（可注是否重试）。
3. 无 path/cmd/决策摘要三类证据之一 → 不得标 completed。

每轮: ①file_read(计划文件) 定位第一个开态（`[ ]`/`[D]`/`[?]`，跳过注释块） ②该步有 SOP→先读 ③查标记: `[D]`=输出压缩为结论+证据路径, `[?]`=评估条件选分支未选标[SKIP] ④无标记主 agent 自己执行 ⑤Mini 验证(file_read 非空/exit code)；失败→按第六章重试→换路径→标[✗]，不静默通过 ⑥file_patch 标 `[✓ 结论 | 证据: …]` 或 `[✗ …]`（禁止裸 ✓；完成后替换行首开态标记，不再保留 `[D]`/`[?]` 作完成态） ⑦立即回①。

**🛑 终止检查**（最后一步标记后, 不可跳过）: file_read(计划文件) 全文扫描, 确认所有步骤(含[VERIFY])均为完成态（`[✓ …]` / `[✗ …]` / `[SKIP …]`），**0 个开态残留**（正文无 `[ ]`/`[D]`/`[?]`；跳过 `<!-- -->`）；输出 `🏁 终止检查：[总步数]步全部完成，0 个开态残留 → 任务结束`; 有遗漏→继续执行, 禁止声称完成。
- ⚠ 若计划文件顶部 HTML 注释/执行协议示例内含开态标记，直接 grep 会误报；终止检查与开态统计均需跳过 `<!-- ... -->` 注释块，或只统计正文计划项。

⚠执行态禁令: 禁凭记忆执行(每步前必 file_read 计划文件) | 禁跳过[VERIFY](不可以"都做完了"为由) | 禁未经终止检查就结束 | 禁停下来输出纯文字进度汇报。

💡输出纪律: 步骤即使未标[D], 遇到读大量代码/文件(>3个或>100行)、反复试错调试、浏览网页提取信息→主动压缩输出为结论+证据路径。保持主 agent 上下文干净是第一优先级。

### 阶段 5：验证态（独立评委自验）
> 🔴 全部步骤[✓]后**强制**主 agent 切换"独立评委"角色做对抗性验证（主 agent 有确认偏误, 易被表面成功迷惑），无例外。对应源码 VerifyPlanExecutionTool 思路。

1. **准备**: `./plan_XXX/verify_context.json` 含 task_description(用户原话)/plan_file/task_type(code|data|browser|file|system)/deliverables(type/path/expected)/required_checks。只传任务描述+plan 路径+交付物+必做检查, **不传**执行过程/调试记录。
2. **自验**: 主 agent 切换"独立评委"角色(提示词: "现在你是独立评委, 忘掉之前的执行历史, 只按计划验证节对抗性验证交付物")。第一步 file_read 计划文件 取「## 验证」节的单条验证命令并实际执行（命令型任务），无命令型按 task_type 选对抗检查；**每个检查必须有工具调用证据**(实际执行非叙述); 输出 result.md, 最后一行 `VERDICT: PASS / FAIL / PARTIAL`; 约束=3轮内、每轮至少1次实际工具调用。
3. **收结果**: 读 result.md 提取 VERDICT。若所有 PASS 项都无工具调用输出(只有叙述)→验证无效按 FAIL 处理。无 VERDICT 行→主 agent 依据 result.md 内容自判。
4. **按结果**: PASS→标[VERIFY]为[✓]、更新 checkpoint `[完成] XXX | [产出] | [经验]`、向用户确认完成(只有 PASS 后才能声称完成); PARTIAL→主 agent 判断可接受则完成否则修复; FAIL→修复循环。

**🔴 修复循环**: 提取失败项→回执行态修复(不重新规划): FAIL 项追加进计划文件 标 `[FIX]`, 只修失败项不重做已 PASS 部分, 修完重备 verify_context.json(只含失败项)→再验证; 最多2轮 FAIL-重试, 超过 ask_user 介入。

**特殊场景**: 浏览器/键鼠/定时任务等: 主 agent 执行并导出证据(截图/录屏/日志)→以独立评委角色验证证据文件。

## 五、验证（SOP 自身的验证）
- 跑完一次规划任务后回读本 SOP：阶段0 判定是否准确？计划文件模板是否够用？
- 检查输出：是否产生 `plan_XXX/plan_XXX.md` + `exploration_findings.md` + `verify_context.json` + `result.md` 四件套
- 检查证据：所有 [✓] 项都有对应工具调用记录（非叙述）
- 经验固化：新增踩坑 → 追加到避坑清单

## 六、失败处理
1. checkpoint 记 `step_X: [FAILED] 原因 (retry: N/3)`。
2. 重试(if-then 三段式):
   - 工具调用失败(code_run/file_read/file_patch 报错)→一线: 自动重试3次(2s/4s/8s); 仍失败→兜底: 换等价路径(webcdp→droid/python→sh/重读SOP)或标[✗]并记 checkpoint。
   - 配置错误/权限不足→一线: 询问用户; 仍失败→兜底: 按用户指示或标[✗]。
   - 其他未知错误→一线: 标[✗]跳过; 仍失败→兜底: 记 checkpoint, 验证态列为必查项。
3. 依赖传播: 步骤失败后, 后续依赖项标[SKIP]。
4. plan 有误: 回规划态修正计划文件, 重新过审查门。

## 强制约束
- 每项必须有独立完成判据。
- 禁止"处理所有文件", 必须展开具体条目。
- 一次只做一项; 计划有误回规划态修正。
- 不可逆操作前多验证一步。
- 计划未经用户确认门（阶段 3）不得执行。
- 探索阶段严格遵守只读约束（阶段 1 🔴）。
- 工具白名单是软约束: code_run 内部操作(shell/python 写文件/重定向/heredoc)同样受阶段文件边界约束(探索态=仅限 plan_XXX/, 执行态=按计划范围), 禁借 code_run 绕过白名单。

## 避坑清单
- ❌ 研究类任务（只收集信息）误入"提交计划审批"流程 → 直接输出发现，不建计划（官方明示）
- ❌ 探索阶段创建/修改文件（违反只读约束）→ 除 plan_XXX 内文件外一律只读
- ❌ 需求模糊就开干 → 先访谈澄清（ask_user）再探索
- ❌ 计划没有多方案权衡 → 官方第③步，必须 ≥2 方案+推荐
- ❌ 计划漏"关键文件" → 实现者不知道动哪些文件
- ❌ 跳用户确认门直接执行 → ⛔ 未确认不得执行
- ❌ 残计划过确认门（漏执行计划/关键文件/验证节）→ 确认门前 file_read(计划文件) 硬校验 3 项
- ❌ 探索漏范围（如只数顶层文件漏子目录）→ exploration_findings.md 必须写「扫描范围确认」客观数字（递归/顶层+数量+子目录）
- ❌ grep '\[ \]' 误报注释块内 [ ] → 终止检查跳过 `<!-- -->` 注释块
- ❌ 无工具调用证据声称 PASS → 按 FAIL 处理
- ❌ 裸 `[✓]` 无结论/证据 → 不得标完成；须 `[✓ 结论 | 证据: path|cmd|决策摘要]`
- ❌ 另建第二套 pending/running/todo 列表替换 checkbox → 只允许映射增强
- ❌ 用户终止后仍留开态 `[ ]`/`[D]`/`[?]` → 一律 `[✗ 用户终止]`，否则终止检查失败
- ❌ 把「完成后形态」示例写进正文执行计划步骤 → 示例仅放 HTML 注释或 fenced，防误计开态
